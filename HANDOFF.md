## What was repaired

**Web:** previously `Client.link()` could return a TorBox CDN link carrying the user's API token. The UI correctly blocked or required disclosure but did not reliably save the file. Added `relay/downloads.mjs`, `POST /api/download-ticket` and `GET /media/:ticket`. Authenticated ticket creation requests the exact TorBox `requestdl` ID, validates HTTPS CDN host, then AES-GCM encrypts the CDN URL and file name into a process-local, 2-minute bearer ticket. Browsers receive only the opaque ticket and the relay streams file bytes with Content-Disposition attachment. No key or CDN URL is put into browser download history; no media is stored by the relay. URL redirects are limited to the same trusted CDN host. Browser UI uses this link for single-file, YouTube and multi-file downloads and retains an explicit Save file fallback. Fix to `Client.request` URL validator permits safe `download-ticket` hyphens: without it, all tests failed.

**Android:** existing Download buttons routed to `openFiles(item)`, showing the chooser and never initiating a single-file save. `MainViewModel.openFiles(... downloadIfSingle=true)` downloads when exactly one ready non-infected file is present, shows a chooser for multiples, and reports zero/infected files as errors. `MainActivity` wires both DownloadsScreen and DownloadDetailScreen Download buttons to it. Existing DownloadManager handoff, progress/status and exact-ID refresh remain in place.

**Preserved:** YouTube link normalization, exact-job status polling (finished AND present), queue/limits, date columns, Compact/Cozy/Detailed spacing, quotas, AirLock, filtering, account handling, Drive, notifications, explicit share confirmations, cancellation and lifecycle handling. No unrelated project changed.
